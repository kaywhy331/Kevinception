TokenPak product expansion

MCP & Knowledge Logistics

A product direction that connects TokenPak to MCP-compatible clients and equips agents with reusable, source-backed, freshness-aware knowledge packages instead of repeated ad hoc research.

Year
2026 R&D
Role
Product strategy · Technical specification · Knowledge architecture · Risk design
Disciplines
MCP · Knowledge systems · AI interoperability · Retrieval · Product architecture
01

The situation

Problem and context

The problem

AI work is fragmented across chat, IDE, CLI, automation, and agent surfaces. At the same time, specialized agents repeatedly rediscover the same facts through model memory, noisy web search, long uploads, or one-off retrieval systems that are expensive and difficult to audit.

Context

The MCP Gateway and Knowledge PAK concepts extend TokenPak from a local context tool into a portable interoperability and knowledge-logistics layer. MCP provides a standardized entrance; TokenPak supplies the differentiated policy, retrieval, packing, memory, budget, routing, receipt, and capture behavior behind it.

Constraints

  • MCP can expose tools and data but cannot guarantee visibility into every host model’s internal context or complete transcript.
  • Source-backed knowledge needs versioning, freshness, authority, citation, and access controls.
  • The first release should be read-first and low-risk before adding mutation, dispatch, or memory-promotion actions.
  • The system must work across local stdio clients and remote streamable HTTP connections.
02

The work

Approach and decisions

  1. 01

    Defined one universal gateway with platform-specific connection profiles rather than separate product integrations.

  2. 02

    Separated the MCP ingress layer from the optional capture companion/proxy needed for deeper observability and routing control.

  3. 03

    Designed a small initial tool surface for status, estimates, budgets, vault search, retrieval, recall, context packing, and receipt reading.

  4. 04

    Specified Knowledge PAKs as versioned, indexed, source-backed bundles refreshed when authoritative sources change.

  5. 05

    Connected every retrieval and action to scoped permissions and receipts.

Key decisions

  • MCP is the standardized entrance, not the complete product moat.
  • The MVP begins read-first; write actions arrive later behind confirmations and receipts.
  • Knowledge is packed into task-specific slices instead of dumping entire corpora into context.
  • Source identity, freshness, and authority are preserved so agents can explain what they relied on.

The evidence

Outcomes

Interoperability model

One gateway, many clientsChat, IDE, CLI, automation, and agent surfaces connect through shared TokenPak contracts.

Knowledge model

Source-backed and reusableKnowledge PAKs are versioned, indexed, refreshed, retrieved in slices, and cited in receipts.

MVP posture

Read-first and governedHigh-risk mutation and dispatch actions are deferred behind explicit permissions and confirmations.

Learning

  • Interoperability standards create reach, but product differentiation still lives in policy, context quality, observability, and trust.
  • Professional agent work needs governed knowledge substrates, not only stronger prompts or larger context windows.
  • Read-first product sequencing creates useful value while giving permission and receipt systems time to mature.
